# ライセンスを AGPL-3.0 とし、OSS 公開・セルフホスト・自社有料サービスを両立させる

## Context and Problem Statement

本プロジェクトを GitHub の public リポジトリとして OSS 公開する。
同時に、将来的には自社が運用する有料サービスとして提供したい。またセルフホストも可能にしたい。

この 3 つを同時に満たすにはライセンス選択が要になる。
ライセンスは一度コントリビューターを受け入れると変更に全員の同意が必要になり、事実上不可逆であるため、公開前に決める必要がある。

## Decision Drivers

* public リポジトリの OSS として公開したい（OSI 承認ライセンスであること）
* 利用者が自分の環境でセルフホストできること
* 第三者が本ソフトウェアをそのまま SaaS 化して競合サービスとして提供することを抑止したい
* 自社が有料 SaaS として提供する道を塞がないこと
* 公開後の変更が困難なため、最初の選択で決着させること

## Considered Options

* AGPL-3.0
* Apache-2.0
* BSL 1.1（Business Source License）

## Decision Outcome

採用した選択肢: 「AGPL-3.0」。
OSI 承認の正規 OSS でありながら、ネットワーク越しにサービスとして提供する場合にも改変部分の公開義務が及ぶため、
第三者によるそのままの SaaS 化を抑止しつつ、セルフホストと自社有料サービスの双方を成立させられるため。

運用方針:

* リポジトリは public、ライセンスは AGPL-3.0（`LICENSE` に全文を置く）
* セルフホストは AGPL の条件下で自由
* 自社が提供する有料サービスは、著作権者としての提供であり AGPL の制約を受けない
* 将来デュアルライセンス（AGPL + 商用ライセンス）を選べるよう、**外部コントリビューターを受け入れる段階で CLA / DCO の導入を検討する**。これを行わない場合、著作権が分散してデュアルライセンス化ができなくなる
* 有料サービスで提供する付加機能（マネージド運用、SSO、利用実績管理など）を別リポジトリに置くかは、必要になった時点で判断する

### Consequences

* Good, because OSI 承認ライセンスであり、「OSS」と名乗れる
* Good, because 第三者がそのまま SaaS 化する場合、改変部分の公開義務が生じるため、無償での競合サービス化を抑止できる
* Good, because 利用者のセルフホストは何ら制限されない
* Good, because 著作権者である自社は、自らの有料サービス提供において AGPL の制約を受けない
* Neutral, because AGPL を社内利用ポリシーで避ける企業があり、Apache-2.0 と比べると採用のハードルは上がる
* Bad, because CLA / DCO を整備しないまま外部コントリビューションを受け入れると、将来のデュアルライセンス化が事実上不可能になる
* Bad, because AGPL の「ネットワーク越しの利用」条項は解釈に幅があり、利用者から適用範囲の問い合わせを受ける可能性がある

### Confirmation

* リポジトリ直下に AGPL-3.0 の全文を含む `LICENSE` が存在すること
* README にライセンス、セルフホスト可能である旨、有料サービスとの関係を明記すること
* 外部からの初回 Pull Request を受け入れる前に、CLA / DCO の要否を判断し結論を記録すること
